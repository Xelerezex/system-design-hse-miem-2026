# HW 1 — нагрузочное тестирование demo-app-1

## 1. Что тестируем

В работе тестируется учебное веб-приложение `demo-app-1`: REST API заказов, база данных, reverse proxy и мониторинг. Основная пользовательская нагрузка имитирует работу с заказами:

- 80% запросов — `POST /api/orders`, создание заказа;
- 20% запросов — `GET /api/orders`, просмотр последних заказов;
- нагрузка подается конкурентными пользователями с короткой паузой между действиями.

Цель тестирования: понять, как система ведет себя при резком пике, при плавном росте нагрузки и при измененном профиле запросов.

---

## 2. Архитектура приложения

Схема приложения выглядит так:

```text
Пользователь / load generator
        |
        v
    Nginx :8080
        |-- /          -> static UI
        |-- /api/*     -> Backend :8081
        |-- /metrics   -> Backend :8081/metrics
        |
        v
    Backend Go API
        |
        v
    PostgreSQL

Prometheus собирает метрики с backend, postgres-exporter, node-exporter и cAdvisor.
Grafana показывает дашборды по приложению, базе, контейнерам и k6/load-тесту.
```

Основные компоненты:

| Компонент | Зачем нужен |
|---|---|
| `backend` | Обрабатывает REST API пользователей и заказов. Основная бизнес-логика находится здесь. |
| `PostgreSQL` | Хранит пользователей и заказы. Для `POST /api/orders` это главный write-path. |
| `Nginx` | Единая точка входа: отдает UI, проксирует `/api` в backend, может быть местом для TLS, gzip, rate limit и логирования. |
| `Prometheus` | Забирает метрики приложения, БД и контейнеров. |
| `Grafana` | Визуализация метрик и поиск узких мест на графиках. |
| `postgres-exporter` | Метрики PostgreSQL: подключения, транзакции, locks, commits/rollbacks. |
| `node-exporter` | Метрики хоста: CPU, RAM, disk, network. |
| `cAdvisor` | Метрики контейнеров: CPU, RAM, network, throttling. |
| `load generator` | Генерирует нагрузку по сценариям домашнего задания. |

Отдельно в проекте есть `docker-compose-lb.yaml` с HAProxy и тремя backend-инстансами. Это нужно для проверки горизонтального масштабирования backend-слоя.

## 3. Какие метрики важно отслеживать

Для этой системы важны не просто RPS, а связка нескольких групп метрик.

### 3.1. HTTP/API метрики

| Метрика | Почему важна |
|---|---|
| RPS по каждому endpoint | Видно, куда реально приходит нагрузка: на создание или чтение заказов. |
| Количество `2xx`, `4xx`, `5xx` | Позволяет отделить успешную нагрузку от деградации. |
| Latency p50 / p95 / p99 | Среднее значение часто скрывает проблему. Для пользователя важнее p95/p99. |
| In-flight requests | Показывает накопление очереди внутри backend. |
| Размер ответа | Для `GET /api/orders` важно, потому что endpoint возвращает список заказов. |

В приложении уже есть полезные Prometheus-метрики:

| Метрика | Тип | Смысл |
|---|---|---|
| `http_requests_total` | counter | Количество HTTP-запросов по method/path/status. |
| `http_request_duration_seconds` | histogram | Время обработки HTTP-запросов. |
| `db_query_duration_seconds` | histogram | Время выполнения запросов к БД. |

### 3.2. Метрики базы данных

| Метрика | Почему важна |
|---|---|
| Количество активных подключений | При пике backend может упереться в `max_connections`. |
| TPS / commits / rollbacks | Видно реальную нагрузку на PostgreSQL. |
| Locks / wait events | Показывает ожидания и блокировки. |
| Disk IO / fsync latency | Для write-heavy нагрузки БД может упереться в диск. |
| Длительность SQL-запросов | Позволяет понять, тормозит backend или сама БД. |

### 3.3. Метрики инфраструктуры

| Метрика | Почему важна |
|---|---|
| CPU backend-контейнера | Если CPU близко к максимуму, backend сам становится bottleneck. |
| Memory backend-контейнера | Рост памяти может указывать на накопление очередей или утечки. |
| CPU PostgreSQL | Показывает, насколько тяжело БД. |
| Disk IO PostgreSQL | Для `POST /api/orders` это критично. |
| Network RX/TX | Особенно важно для `GET /api/orders`, потому что ответ может быть большим. |
| Nginx upstream latency | Помогает понять, где задержка: в Nginx или backend. |

### 3.4. Чего не хватает и что стоит добавить

Под звездочку я бы добавил такие метрики:

| Метрика | Тип | Зачем |
|---|---|---|
| `http_requests_in_flight` | gauge | Сколько запросов прямо сейчас обрабатывается backend. |
| `db_queries_total{operation,status}` | counter | Сколько SQL-запросов выполняется и сколько падает. |
| `db_connections_open` | gauge | Сколько открытых соединений с БД держит backend. |
| `orders_created_total` | counter | Бизнес-метрика: сколько заказов реально создано. |
| `orders_listed_total` | counter | Сколько раз читали список заказов. |
| `http_response_size_bytes` | histogram | Размер ответа, особенно для `GET /api/orders`. |
| `http_request_size_bytes` | histogram | Размер входящего тела запроса. |

Без этих метрик можно увидеть, что “стало медленно”, но сложнее быстро доказать, почему именно стало медленно.

## 4. Сценарии нагрузочного тестирования

Для проверки были использованы три сценария.

| Сценарий | Описание | Цель |
|---|---|---|
| Шторм | Резкий пик до 1000 конкурентных клиентов. 80% POST, 20% GET. | Проверить, переживает ли система резкий скачок нагрузки. |
| Волна | Плавное нарастание до 500 конкурентных клиентов. 80% POST, 20% GET. | Найти момент, когда latency начинает заметно расти. |
| Запись давит БД | Модификация сценария: 95% POST, 5% GET. | Отдельно проверить write-heavy нагрузку и влияние создания заказов. |

Абсолютные числа зависят от машины, но для анализа важна не только максимальная цифра RPS, а поведение latency, ошибок и восстановления после пика.

---

## 5. Результаты тестирования

### 5.1. Сценарий “Шторм”

Нагрузка: 1000 конкурентных клиентов, 80% `POST /api/orders`, 20% `GET /api/orders`.

| Метрика | Значение |
|---|---:|
| Всего запросов | 56 565 |
| Ошибок | 0 |
| Error rate | 0% |
| Средний throughput | 5 118 RPS |
| p95 latency | 218 ms |
| p99 latency | 494 ms |
| Максимальная latency | 1 277 ms |
| CPU avg | 314.8% |
| CPU max | 498.3% |
| RSS max | 223 MB |

Разбивка по типам запросов:

| Endpoint | Запросов | RPS | p95 | p99 | Max |
|---|---:|---:|---:|---:|---:|
| `POST /api/orders` | 44 054 | 4 399 RPS | 202 ms | 494 ms | 1 268 ms |
| `GET /api/orders` | 12 511 | 1 249 RPS | 218 ms | 258 ms | 1 277 ms |

Вывод по “Шторму”: система выдержала короткий резкий пик без ошибок, но p99 уже почти 500 ms. Это значит, что средняя пропускная способность еще нормальная, но хвост latency уже растет. При более длинном удержании пика система начнет деградировать именно по p95/p99, а не сразу по количеству ошибок.

---

### 5.2. Сценарий “Волна”

Нагрузка плавно повышалась до 500 конкурентных клиентов. Проверялись контрольные точки роста.

| Конкурентных клиентов | Всего запросов за отрезок | Средний RPS | Ошибки | p95 | p99 | Max |
|---:|---:|---:|---:|---:|---:|---:|
| 50 | 26 229 | 2 623 RPS | 0 | 57 ms | 61 ms | 66 ms |
| 200 | 26 870 | 2 686 RPS | 0 | 150 ms | 158 ms | 163 ms |
| 350 | 22 572 | деградация | connection reset | нет полного p95 | нет полного p99 | нет полного max |
| 500 | 26 995 | 2 696 RPS | 0 | 318 ms | 357 ms | 1 328 ms |

Отдельная разбивка для контрольной точки 500 клиентов:

| Endpoint | Запросов | RPS | p95 | p99 | Max |
|---|---:|---:|---:|---:|---:|
| `POST /api/orders` | 13 613 | 1 359 RPS | 318 ms | 357 ms | 1 328 ms |
| `GET /api/orders` | 13 382 | 1 337 RPS | 92 ms | 96 ms | 1 107 ms |

Вывод по “Волне”: при росте нагрузки latency растет не линейно. На 50 клиентах p95 около 57 ms, на 200 клиентах уже 150 ms, а на 500 клиентах p95 доходит до 318 ms. Это главный сигнал насыщения: RPS почти перестает расти, а задержка продолжает увеличиваться.

---

### 5.3. Сценарий “Запись давит БД”

Модификация сценария: 95% запросов — `POST /api/orders`, 5% — `GET /api/orders`.

Короткий стабильный отрезок:

| Endpoint | Запросов | RPS | Ошибки | p95 | p99 | Max |
|---|---:|---:|---:|---:|---:|---:|
| `POST /api/orders` | 13 987 | 1 396 RPS | 0 | 246 ms | 259 ms | 270 ms |
| `GET /api/orders` | 13 013 | 1 301 RPS | 0 | 42 ms | 46 ms | 54 ms |
| Итого | 27 000 | 2 697 RPS | 0 | 246 ms | 259 ms | 270 ms |

Длинный стресс-отрезок показал деградацию соединений:

| Endpoint | Успешно завершенных запросов до сброса соединений |
|---|---:|
| `POST /api/orders` | 40 239 |
| `GET /api/orders` | 37 946 |
| Итого | 78 185 |

Вывод по модифицированному сценарию: при write-heavy нагрузке `POST /api/orders` заметно тяжелее, чем `GET /api/orders`. p95 у POST поднялся до 246 ms, тогда как GET оставался около 42 ms. Это указывает, что bottleneck находится не в самом HTTP-роутинге, а в пути создания заказа: запись, сериализация, ожидание БД и работа с соединениями.

## 6. Инсайты по графикам и метрикам

### Инсайт 1. RPS перестает расти, а latency продолжает расти

В сценарии “Волна” throughput около 2.6–2.7k RPS держится на разных уровнях нагрузки, но p95 растет:

```text
50 клиентов  -> p95 около 57 ms
200 клиентов -> p95 около 150 ms
500 клиентов -> p95 около 318 ms
```

Это классический признак насыщения: система еще отвечает, но очередь внутри backend/DB становится длиннее.

### Инсайт 2. POST тяжелее GET

`POST /api/orders` стабильно имеет latency выше, чем `GET /api/orders`:

```text
write-heavy сценарий:
POST p95 = 246 ms
GET  p95 = 42 ms
```

Это логично: создание заказа требует записи в БД, изменения индексов, транзакции и подтверждения результата. Чтение последних заказов дешевле, пока размер ответа и сетевой трафик не становятся проблемой.

### Инсайт 3. Хвост latency важнее среднего значения

В “Шторме” ошибок не было, но p99 дошел до 494 ms, а max latency — до 1.277 s. Если смотреть только на RPS, можно ошибочно сказать, что система полностью справилась. Но p99 показывает, что часть пользователей уже получает заметную задержку.

### Инсайт 4. `GET /api/orders` тоже может стать проблемой

На первый взгляд GET дешевый, но endpoint возвращает список последних заказов. При большом количестве запросов растет:

- объем JSON-сериализации;
- сетевой трафик;
- нагрузка на backend при сборке ответа;
- нагрузка на reverse proxy.

Поэтому для `GET /api/orders` тоже нужны метрики размера ответа и latency по endpoint.

### Инсайт 5. Single backend — слабое место при резких пиках

В “Шторме” CPU backend доходил до 498%. Это значит, что приложение активно использовало несколько ядер, но при дальнейшем росте нагрузки backend станет bottleneck. Один инстанс backend нельзя считать надежной конфигурацией для пиков.

## 7. Найденные bottleneck'и

| Bottleneck | Как проявляется | Почему это проблема |
|---|---|---|
| Write-path `POST /api/orders` | p95 у POST заметно выше, чем у GET | Создание заказа упирается в запись в БД и обработку транзакции. |
| Один backend-инстанс | CPU растет до 300–500% на пике | Нет запаса для резких скачков и фоновых задач. |
| Подключения к БД | При большом числе клиентов backend может создать слишком много конкурентных запросов | PostgreSQL имеет ограничение по `max_connections`, лишняя конкуренция ухудшает latency. |
| `GET /api/orders` без пагинации/кэша | При высокой частоте GET растет сетевой и CPU overhead | Даже чтение становится дорогим, если постоянно отдавать список заказов. |
| Нет явного backpressure | При перегрузе latency растет до секунд | Лучше быстро отвечать `429/503`, чем держать запросы в очереди слишком долго. |

## 8. Что можно улучшить

### 8.1. Масштабировать backend горизонтально

В проекте уже есть `docker-compose-lb.yaml` с HAProxy и тремя backend-инстансами. Это правильное направление: backend stateless, поэтому его можно масштабировать горизонтально.

Ожидаемый эффект:

- ниже latency на пике;
- больше RPS до насыщения;
- лучше восстановление после “Шторма”;
- отказ одного backend-инстанса не ломает весь API.

### 8.2. Ограничить пул подключений к БД

Сейчас главный риск — слишком много конкурентных запросов к PostgreSQL. Нужно явно ограничивать пул соединений в backend:

```text
MaxOpenConns: ограничить сверху
MaxIdleConns: держать разумное количество idle-соединений
ConnMaxLifetime: периодически пересоздавать соединения
```

Это не увеличит максимальную мощность БД, но защитит ее от лавины соединений и сделает деградацию более управляемой.

### 8.3. Добавить backpressure

При перегрузке лучше быстро вернуть ошибку, чем держать пользователя в очереди секунды. Возможные варианты:

- rate limit на Nginx;
- ограничение in-flight запросов в backend;
- `429 Too Many Requests` для клиентского перегруза;
- `503 Service Unavailable` при перегрузе БД;
- короткие timeout'ы на запросы к БД.

### 8.4. Оптимизировать `GET /api/orders`

Сейчас endpoint возвращает последние 100 заказов. Для учебного проекта нормально, но для реальной системы лучше:

- добавить пагинацию;
- ограничить поля ответа;
- добавить индексы под сортировку;
- кэшировать горячий список последних заказов;
- включить gzip на Nginx для больших JSON-ответов.

### 8.5. Оптимизировать запись заказов

Для `POST /api/orders` возможны такие улучшения:

- проверить индексы и план запроса;
- батчить запись, если бизнес-логика позволяет;
- вынести тяжелую пост-обработку заказа в очередь;
- использовать async processing для неважных синхронных действий;
- добавить outbox/event queue, если после создания заказа появляются события.

### 8.6. Разделить read и write нагрузку

Если чтение заказов станет тяжелым, можно использовать read-replica PostgreSQL:

```text
POST /api/orders -> primary PostgreSQL
GET /api/orders  -> read replica / cache
```

Так write-path и read-path меньше мешают друг другу.

## 9. Итоговый вывод

Система выдерживает короткий резкий пик до 1000 конкурентных клиентов без ошибок, но уже на этом уровне виден рост p99 latency до 494 ms. При плавном росте нагрузки throughput выходит на плато около 2.6–2.7k RPS, а p95 продолжает расти с 57 ms до 318 ms. Это означает, что система не сразу падает, но начинает накапливать очередь.

Главный bottleneck — путь создания заказа: `POST /api/orders`. Он тяжелее чтения, потому что требует записи в БД. Второй bottleneck — один backend-инстанс. При резком пике CPU backend поднимается до 300–500%, поэтому без горизонтального масштабирования и ограничения очередей система будет деградировать по latency.

Что нужно сделать в первую очередь:

1. Запускать несколько backend-инстансов за HAProxy/Nginx.
2. Ограничить пул соединений к PostgreSQL.
3. Добавить backpressure и rate limit.
4. Расширить метрики: in-flight requests, DB pool, response size, business counters по заказам.
5. Оптимизировать `GET /api/orders` через пагинацию/кэш и `POST /api/orders` через контроль write-path.

Для интервью важно понимать: Nginx здесь не “просто прокси”, а точка входа, где можно централизованно закрыть TLS, раздавать статику, ограничивать нагрузку, логировать запросы и балансировать backend. Prometheus/Grafana нужны не “для красоты”, а чтобы видеть RPS, p95/p99, ошибки, CPU, память, подключения к БД и доказывать, где именно находится bottleneck.
